# Phase A3.2: occupancy engine migration (audit and design)

Baseline: integration 0.6.10, App 0.3.0 (main 065c5d4). This document was written
before any runtime change. It records which components depend on room occupancy, and
how the occupancy engine moves to the App without changing behaviour.

## 1. Dependency inventory

### 1.1 The engine and its runtime (integration)

| Component | Role |
|---|---|
| `engine.py` | Pure state machine per room (`RoomEngine`, `SignalTrack`, `RoomResult`). HA-independent apart from importing enums and dataclasses from `const.py` and `models.py`. |
| `occupancy_manager.py` | HA runtime around the engines. It has one state subscription for every signal and reference helper, and one timer per room at `next_deadline`. It routes neighbour motion, resyncs at start-up, handles preliminary signals, zone holds and wall-switch activity, keeps the `ComparisonTracker` (reference helper), and stores `.storage/smart_occupancy.occupancy_state` on transitions (15 s debounce). It notifies per-room listeners after each evaluation. |
| `coordinator.py` | Builds the OccupancyManager. Calls `async_reconfigure` for live presence changes (`async_apply_presence`), and records transitions in the presence log. |
| `models.py` / `const.py` | `SensorAssignment`, `OccupancyTiming`, `TIMING_PARAMETERS`, `OccupancyState`, `SensorKind`, `SensorRole`. The authoritative configuration lives in the config entry options. |

### 1.2 Inputs that do not come from sensors

| Input | Producer | API |
|---|---|---|
| Preliminary (possible-occupancy lighting) signals | `controller._sync_preliminary_signals` | `OccupancyManager.async_set_preliminary(dict[area, frozenset])` |
| Zone holds | `zone_runtime._sync_holds` (zone engines are `RoomEngine`s too) | `async_set_holds(area, names)` |
| Wall-switch activity evidence | `switch_control` (switches with `activity_evidence`) | `async_note_activity(area, source)` |
| Neighbour motion | internal: a capable signal starting in room A notifies the rooms that list A as adjacent | `RoomEngine.note_neighbour_motion` |

**Circular dependency.** Zone runtime reads the room result (`result()` plus a listener), and its holds feed back into the room engine. A hold can only *keep* an occupied room occupied, so this loop cannot make a room occupied by itself. Across a process boundary the loop becomes asynchronous. The hold timestamp is carried along, so the room's quiet period starts when the zone ended, not when the message arrived.

### 1.3 Consumers of occupancy results

All of them read `coordinator.occupancy.result(area_id)` (a `RoomResult`) and/or register `occupancy.async_add_listener(area_id, cb)`:

* room entities (`entity.py`, `sensor.py`, `binary_sensor.py`): state, occupied, reason, confidence, last activity (`sensor.py` also reads `engines[a].tracks` for a name);
* lighting (`controller.py`: about 30 reads, the occupancy listener for activation, vacancy and preliminary stages; `lighting_decisions.py`, `preliminary.py`, `preliminary_websocket.py`, `supervisor.py`, `websocket.py`);
* zones (`zone_runtime.py`), shared spaces (`controller` reads several rooms);
* curtains (`curtains/auto.py`: the manual hold "until the room is empty", listener);
* forecasts (`forecast.py`: listener, `result()`, neighbouring rooms) and the Recorder-backed `prediction.OccupancyHistory` (`history.record` on every transition);
* the presence API (`presence_api.py`: `engines[a]` for signal details, explain and predict, `comparison()`), `rooms_api.py`, `health.py`, `diagnostics.py`;
* the presence log (`on_transition`).

`forecast_history.py` replays Recorder history through its own `RoomEngine` instances. These are offline and not affected.

**Consequence:** `OccupancyManager.result()` plus its listeners is already a single, stable occupancy-result interface. The migration keeps that interface and changes only *where the published result comes from*. No consumer gets a second data path.

### 1.4 Persistence

* `.storage/smart_occupancy.occupancy_state` (v1): per room the engine's `persist()` and the comparison counters. It stays exactly as it is and keeps being written by the integration's own engine.
* Presence log: memory only (`hass.data`).

## 2. Design decisions

### 2.1 Shared engine: `occupancy_core` (one implementation, two copies, enforced identical)

The HA-independent logic moves into a package without dependencies:
`custom_components/smart_occupancy/occupancy_core/`. HACS installs only that folder, so the package must live inside it. The App's Supervisor build context is `smart_lighting/` only, so the App carries a **byte-identical vendored copy** at `smart_lighting/backend/occupancy_core/`. Nothing is downloaded at runtime.

* `types.py`: enums, `TIMING_PARAMETERS`, `SensorAssignment`, `OccupancyTiming`. `const.py`/`models.py` re-export them, so object identity is unchanged.
* `engine.py`: the 0.6.10 engine, moved verbatim, plus three additions for the migration: `export_state`/`import_state` (exact, versioned state transfer) and `adopt` (conservative reconciliation of another engine's decision).
* `house.py`: the HA-independent part of `OccupancyManager`: routing (entity → rooms, neighbour motion), the start-up resync rule, live reconfiguration, preliminary, holds, activity, evaluation and transition detection, deadlines, persistence. The integration's manager and the App runtime are both thin adapters around it.
* `wire.py`: validated JSON forms of the spec (configuration), results, inputs and engine state.
* `protocol.py`: bridge protocol constants and message validation.
* `golden.py` + `golden/*.json`: scenario fixtures with expected transitions and reason codes.

Compatibility is enforced in three ways:

1. A test fails when the two copies differ by one byte (`scripts/sync_occupancy_core.py` copies them).
2. `CORE_VERSION` plus a SHA-256 **fingerprint** of the package sources is exchanged on the bridge. The integration refuses a handover to an App whose fingerprint differs.
3. A frozen copy of the 0.6.10 engine (`tests/legacy_engine_0610.py`) and differential tests (golden fixtures and randomised event sequences) prove that the core engine gives the same result at every evaluation. The App also runs the golden fixtures at start-up and reports the result as a readiness check.

### 2.2 App runtime

`OccupancyRuntime` (App backend) holds a `House` built from the integration's spec. It uses the App's existing websocket (`state_changed` events with HA's `last_changed`), plus one asyncio timer per room at `next_deadline`. Its state is stored in `/data/occupancy/state.json` (versioned, validated, written on transitions only and debounced, with backups kept). It never sends a service call: `ha.py`'s allowlist has no command that can do so.

**Reference start.** While the integration's engine runs, each new bridge session begins with an exact copy of the integration engine's state (`export_state`). This applies to the first connection, after a reconnect, after an HA restart and after an integration reload. After that, both engines evolve independently on the same event stream, which is what the comparison measures. It also means an App restart or a network gap never invents a decision: events missed while disconnected are covered by the copy and a state resync. The App's own stored state is used only when the integration's engine is not reachable.

### 2.3 Bridge and ownership (central authority: the integration)

Transport: the existing HA websocket through the Supervisor proxy. There is no new port and no public endpoint. All commands need an administrator (`require_admin`). The App's backend sends them only through a dedicated allowlist in `ha.py`.

| Command | Purpose |
|---|---|
| `smart_occupancy/engine/subscribe` | Opens a bridge session (instance id, versions, fingerprint, protocol). Streams `hello` (spec and revision, boot id, ownership, inputs, full engine state, results), `spec`, `inputs`, `results` (the integration engine's and the published), `ownership`, `closed`. |
| `smart_occupancy/engine/status` | Ownership record, lease, sessions, versions, history, freshness. |
| `smart_occupancy/engine/claim` | Reviewed handover (compare-and-swap on `expected_epoch`; versions, fingerprint and config revision must match; the readiness summary is recorded). |
| `smart_occupancy/engine/publish` | The owner's results (epoch, lease token, sequence, config revision). |
| `smart_occupancy/engine/heartbeat` | Renews the lease. |
| `smart_occupancy/engine/release` | Returns control to the integration. Also available as the admin-only service `smart_occupancy.engine_return_to_integration`, so rollback works without the App. |

The ownership record (`.storage/smart_occupancy.engine_ownership`) is the only authority:
`owner` (integration | app), monotonically increasing `epoch`, owner instance and session, lease token hash, lease, config revision, fingerprint, last sequence, and a bounded history.

Fencing rules (integration side):

* Only messages from the session that holds the lease, on the same websocket connection, with the current `epoch`, a matching lease token and the current config revision are accepted.
* `seq` must strictly increase. Duplicates and reordered messages are refused.
* Every ownership change increments `epoch`. A previous owner's in-flight messages are refused (`stale_epoch`), which tells it that it lost ownership.
* The published result per room is chosen by the integration alone: the owner's latest accepted result in the current epoch, otherwise the integration engine's result. Two engines cannot both be authoritative.

Lease: 30 s, heartbeat every 10 s (lease renewed by every accepted publish). An HA restart or integration reload while the App owns occupancy enters *resume pending* for 120 s. During that time the integration engine publishes (restored conservatively with the start-up hold, exactly as before). The *same App process* may resume with its lease token. Otherwise the integration falls back. A bridge session from a different App instance (an App restart or upgrade) makes the integration fall back at once. **A recovered App never takes ownership back.** It returns to shadow mode until an administrator performs a new reviewed handover.

### 2.4 Hot standby and fallback

The integration's engine never stops. It keeps observing every signal and input while the App owns occupancy. This makes fallback continuous:

1. The integration fences the old owner (`epoch + 1`, `owner = integration`).
2. Per room, if the integration engine agrees with the last accepted App decision (state and occupied), nothing changes. Otherwise it **adopts** that decision conservatively: a room that was occupied stays occupied and its quiet period restarts at the fallback moment. So communication loss never causes vacancy, and a vacancy countdown is extended, never shortened.
3. The published result switches only if it actually differs. Listeners are notified only on a change, so a handover or fallback with equal decisions sends no command to any device.

Handover (integration → App) uses the exact state copy, so the first App result equals the integration's.

### 2.5 Shadow comparison (App)

The App compares its engine's results with the integration engine's results streamed over the bridge, per room. A discrepancy episode opens when state or occupied differ. If it closes within 3 s it counts as a *timing difference*; otherwise it is a *disagreement*, stored together with the room's recent input events. Vacancy deadlines are compared with a tolerance of 2 s; reason codes are compared at transitions. History is bounded (200 records) and stored in `/data/occupancy/comparison.json`.

Handover readiness (all required):

* bridge connected;
* protocol supported;
* identical core version and fingerprint;
* golden self-test passed;
* config revisions equal;
* integration currently the owner;
* shadow comparison running for at least 2 h;
* at least 20 matched transitions;
* no disagreement in that window;
* every room agreeing now.

### 2.6 GUI

Presence → **Engine** (`#/presence/engine`) shows:

* the authoritative engine *as acknowledged by the integration*, with epoch and lease freshness;
* connection, versions and fingerprint, configuration sync, last accepted result and self-test;
* comparison statistics, a per-room comparison and the discrepancy list with events;
* readiness checks, the reviewed handover and a prominent **Return control to integration**;
* ownership history.

The Presence dashboard shows the owner. The floor-plan Presence overlay keeps showing the published entities and can mark rooms where the shadow engine disagrees.

## 3. Behaviour that must not change

* Every rule of the 0.6.10 engine, and the integration's start-up and reload behaviour.
* Entity ids and unique ids.
* Default ownership is the integration. Installing or upgrading the App or the integration never changes the owner. The legacy engine stays in place, and its removal is a later phase.

## 4. Limitations accepted in this phase

* Comparison time and thresholds are fixed constants. Development and test runs can lower them through environment variables only.
* The integration's engine keeps running as hot standby. CPU cost is that of 0.6.10 (event driven).
* Real HAOS/Supervisor hardware was not available. Verification uses a throwaway Home Assistant 2026.11 and the real App container with a fake Supervisor.
